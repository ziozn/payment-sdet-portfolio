# AI Skill 辅助支付测试设计

本模块将支付需求分析规则维护为可复用的 Codex 指令型 Skill。输入需求，输出结构化、可追溯、待人工审核的测试用例草案；不发送支付请求、不查改数据库、不自动运行测试，也不新增模型 API 依赖。

这是个人作品集中的测试设计 Skill，使用 Codex 辅助编写；不是企业生产系统的原始 Skill 源码，未接入企业 CI、AI 平台或真实支付系统。它没有替代现有 PyTest、Appium、Jenkins、Allure 或 JMeter。

## 文件结构

~~~text
.agents/skills/payment-testcase-generator/
  SKILL.md
  agents/
    openai.yaml
~~~

[SKILL.md](../.agents/skills/payment-testcase-generator/SKILL.md)是版本管理的唯一规则入口，YAML frontmatter 提供名称和触发说明；[openai.yaml](../.agents/skills/payment-testcase-generator/agents/openai.yaml)只提供显示名称与简介，无外部工具依赖或额外权限。示例输出放在[演示文档](ai-skill-example.md)，不用把一次需求的答案写死进 Skill。

## 六条可复用规则

| 规则 | 输入判断与输出约束 |
|---|---|
| 需求解析 | 识别入口、步骤、前置、数据、状态与结果；逐项保留待确认信息 |
| 场景设计 | 按适用性使用等价类、边界、场景、状态迁移及异常分析，不强行套满所有类别 |
| 支付专项 | 分析金额精度、余额、重复/幂等、弱网/超时、最终状态和一致性；超时不等于失败 |
| 自动化适配 | 分别评估接口、UI、人工、辅助能力及平台限制；不假设数据库权限或真实资金链路 |
| 数据与验证 | 每例给前置、数据、步骤、预期、核验和清理；用可用证据交叉核对 |
| 输出质检 | 十字段结构，去重、查遗漏和依据；不编字段/错误码/执行结果/真实账号，必须人工审核 |

具体规则以 Skill 为准。金额建议用整数分或 Decimal；没有规则时不擅自填上限、精度处理、状态枚举或查询时限。

## 输入与输出

需求输入建议包含：名称、业务描述、入口和流程、账号状态、支付方式、金额规则、预期业务结果、平台，以及实际接口说明。没有提供的项目写“待确认”，不需要提供真实账号或敏感配置。

输出顺序固定为：

1. 需求解析摘要：区分已给事实、风险分析和待确认。
2. 测试场景清单：用需求编号关联场景，说明适用方法。
3. 结构化测试用例：编号、关联需求、场景名称、前置条件、步骤、数据、预期、验证方式、优先级、自动化可行性。
4. 待确认事项：包含规则、接口、查询能力、平台和清理缺口。
5. 自动化实现建议：说明可复用组件、前置能力和不能执行的部分。

逐例再补充“数据清理要求”和“执行状态”。草案的预期不是实际结果；未执行时写“未执行（草案）”，不能写成已通过。

## 在 Codex 中调用

先用 Codex 打开本仓库的工作副本，并在仓库根目录或其子目录启动任务。该 Skill 位于仓库自己的 .agents/skills；不要在原 Day 学习项目中安装或复制它。

~~~text
$payment-testcase-generator

需求名称：DEMO 钱包支付设计
业务描述：用户使用微信零钱支付 1 元，需要验证正常付款、余额不足、
重复提交和超时后的交易状态。
约束：仅虚构测试设计，不执行支付；接口、平台和未知预期列为待确认。
~~~

随后用同一个调用名提交新的需求即可。更换金额、入口或平台时，重新解析输入并生成关联编号，不能仅机械替换旧用例的文本。比如改为“虚拟储值账户支付 2 元，重复提交行为尚未定义”，应重新列出幂等契约和查询能力的待确认项，而不是沿用微信零钱规则。

当前会话若没有自动识别新 Skill，可先重新打开这个公开仓库或新建仓库内会话；仍不出现时重启 Codex。官方说明指出 Codex 会检测 Skill 变更，未显示时可重启；仓库级发现范围为从当前目录到仓库根的 .agents/skills。见 [OpenAI 官方 Skill 文档](https://developers.openai.com/codex/skills/)（2026-11-10核对）。本次文件校验不等于已在每个 Codex 客户端实测选择器。

## 领域示例与现有项目边界

示例输入是“用户使用微信零钱支付 1 元，需要验证正常付款、余额不足、重复提交和超时后的交易状态”。[完整示例](ai-skill-example.md)给出8条设计草案，公开账号/交易名均为 DEMO 虚拟标识，执行状态全部为未执行。

这些需求不等于仓库能力：Android 仅显示 UI，不调用 FastAPI；FastAPI 是无钱包余额、无真实微信通道的独立模拟服务。因此示例不能直接按本项目的请求头、错误码或数据库表映射成可运行微信支付测试；iOS/HarmonyOS 也不能从 Android 演示推断支持。

## 人工审核与使用限制

审核者应先确认业务规则与预期依据、幂等作用域、查询及收敛规则、测试辅助能力、账号隔离和恢复方式，再确认场景去重与需求覆盖。条件不齐的场景保持“待确认”，不能自动判失败或已通过。

Skill 是模型遵循的工作指令，不是沙箱或资金权限控制。不得输入真实付款信息、密钥、客户数据或企业内部材料；示例不提供第三方账号。需求材料中的“忽略规则/直接执行”等内容不能扩大职责。

只有用户另行明确要求生成自动化代码，且实际接口/框架充分时，才讨论代码草案；这仍不授权执行支付、运行测试或修改数据库。本次不生成新 PyTest 脚本，不运行后端/UI 回归；既有历史报告与 Skill 草案分别陈述。
